# Стандарты СТО в структуре EA

Работа со стандартами: JSON собирается по модели `EA/structure.eapx`
(`EA/docx2json.py`) и приводится к актуальной модели `EA/structure2.xml`
(`ea_schema.py`, `tools/migrate_standards_structure2.py`), а редактор схем
читает его через `ea_standard.py`: показывает в окне `ea_ui.py`, ставит
шкафы и комплекты на схему (`ea_catalog.py`), делает новый стандарт на базе
выбранного (`ea_new_standard.py`) и выгружает документ в Word (`ea_docx.py`).

## Формат

```
Standard
├── title_page                                   (DOCX титульного листа)
├── Section → Subsection → Clause → Subclause   (текст документа)
│   └── Table / Figure                          (таблица — только форма)
├── Cabinet → Kit → IED                          (данные)
│                └── scheme                     (файл ФЛС редактора)
└── FunctionalBlocks → FunctionalBlockEntry     (каталог блоков для схемы)
    └── functions → inputs / outputs /
                    settings / parameters
```

Ключевое правило: **данные хранятся один раз — в `cabinets`**. Таблица в
разделе СТО содержит номер, название, ссылку и форму (шапку), а также поле
`cabinet` — шифр шкафа, из которого берутся строки:

```json
{
  "number": "5.3",
  "name": "Входные аналоговые измерения ИЭУ ШЭТ 431.11-1",
  "reference": "Таблица 5.3",
  "cabinet": "ШЭТ 431.11-1",
  "rows": [{"content": ["Аналоговая цепь", "..."], "is_header_first_row": true}]
}
```

У «Описание ШЭТ» форма — ключи первого столбца с пустыми значениями:
значения подставляет шкаф. Таблицы вне шкафов (термины, сокращения,
применимость, библиография) хранят данные сами — им неоткуда их тянуть.

## Функции, слоты, уставки и параметры

Функции ИЭУ хранятся не плоским списком, а блоками — как в
`EA/structure2.xml`:

```
IED
├── functional_keys, leds, ...           (прочие данные ИЭУ)
└── function_blocks
    └── FunctionBlock                    блок (группа, «ДТЗ»)
        └── functions                    функции блока
            ├── inputs / outputs         слоты с типом
            ├── settings                 уставки
            └── parameters               параметры
```

```json
{
  "name": "ДТЗ",
  "isMainFunction": true,
  "isInITS": false,
  "iec_name": "PDIF",
  "russian_path": "ДТЗ",
  "corp_prof_name": "ДТЗ",
  "functions": [{
    "name": "Дифференциальная защита",
    "iec_name": "PDIF1",
    "LNclass": "PDIF",
    "inputs": [{"name": "IA", "iec_name": "TCTR1.AmpSv", "slot_type": "analog_process_level"}],
    "outputs": [{"name": "Срабатывание", "iec_name": "PDIF1.Op", "slot_type": "control_operation"}],
    "settings": [{"name": "Уставка срабатывания", "value": "0.2", "unit": "о.е."}],
    "parameters": [{"name": "Режим", "value": "Вкл", "description": "..."}]
  }]
}
```

Тип слота — одно из значений `SlotTypes` модели: `analog_process_level`,
`discrete_process_level`, `control_operation`, `internal_info_exchange`,
`external_info_exchange`. Тип задаёт вид связи ФЛС
(`ea_model.LINK_KIND_BY_SLOT`) и подпись в редакторе
(`ea_model.slot_type_title`).

Доступ к модели — [`ea_model.py`](ea_model.py): `function_blocks(ied)` читает
`function_blocks` или собирает их из старого плоского `functions`,
`iter_functions(ied)` обходит функции всех блоков, `normalize_*` приводят
поля к общему виду (`conditions` → `value` у параметра), `migrate_document()`
переводит стандарт на новую структуру. `ea_standard.py` переэкспортирует
этот API, поэтому остальные модули работают с функциями одинаково.

Файлы стандартов уже переведены на `function_blocks`
(`tools/migrate_standards_structure2.py`, повторный запуск безопасен);
старый формат с `functions` продолжает читаться.

## FunctionalBlocks — отдельный модуль стандарта

По аналогии с `cabinets`, все блоки функций ИЭУ стандарта собраны в плоский
каталог `Standard.functional_blocks`. Запись `FunctionalBlockEntry` — это
полная копия `FunctionBlock` плюс поля принадлежности `cabinet`, `kit`, `ied`:

```json
{
  "cabinet": "ШЭТ 431.11-1", "kit": "1", "ied": "1",
  "name": "ДЗШ", "iec_name": "", "russian_path": "ДЗШ",
  "isMainFunction": true, "isInITS": true,
  "functions": [{ "name": "ПО", "iec_name": "", "LNclass": "",
                  "inputs": [], "outputs": [],
                  "settings": [], "parameters": [] }]
}
```

Каталог не дублирует ручной ввод: если в JSON его ещё нет, `ea_standard.py`
 собирает записи из шкафов на лету (`all_functional_blocks()`), поэтому блоки
 видны сразу после открытия стандарта. Кнопка «Пересобрать ФБ» в окне
 стандарта (или контекстное меню раздела «Функциональные блоки» редактора)
 записывает каталог в JSON и позволяет править записи вручную. Команда
 `python ea_standard.py <файл.json> --fb` печатает каталог.

У блоков функций в стандарте поля МЭК и выходы обычно пусты. Полные
наименования и атрибуты берутся из таблиц «Информационные сигналы в составе
исходящих отчетов/сообщений» (`datasets[].signals[]`): `name` хранит русскую
связку `ФБ / Функция: Сигнал`, а `DO`/`DA` (или `info_model`) — МЭК-путь.
`ea_standard.enrich_function_block()` разбирает эти поля и добавляет в
каталог выходы функций с русским именем, полным МЭК-обозначением и полной
русской маркировкой в `description`. Оттуда же берутся МЭК-обозначения блока
и функции. Генерация ФЛС из ИЭУ использует тот же источник.

МЭК-путь хранится и по частям: в `FunctionBlock`, `Function`, `Input`,
`Output` и `FunctionalBlockEntry` есть поля `LD`, `LN`, `DO`, `DA` (у `Signal`
добавлены `LD`/`LN` к уже существующим `DO`/`DA`). Например, для сигнала
`ЗП / ЗП: Срабатывание` с `DO = CMROVCTOC/PTOC1.Op`, `DA = general`:

```
LD = CMROVCTOC   LN = PTOC1   DO = Op   DA = general
iec_name = CMROVCTOC/PTOC1.Op.general
```

Поля доступны в редакторе стандарта, в свойствах блока и функции ФЛС и
сохраняются в JSON схемы — их можно использовать в других отчётах без
повторного разбора строки. `ea_model.iec_parts()` — общий помощник.

Выбранную запись можно сразу поставить на схему кнопкой «ФБ → на схему»:
`main.py` создаёт элемент ФЛС `logic_block` с русским именем и МЭК-обозначением,
принадлежностью к шкафу/комплекту/ИЭУ и всеми функциями (сигналы, уставки,
параметры). Поля принадлежности сохраняются в JSON схемы и доступны в
свойствах блока. При создании нового стандарта каталог фильтруется по
оставленным шкафам; при слиянии — пересобирается.

Тот же каталог питает **монтажную схему шкафа**: в окне ИЭУ (`mount_ied`)
кнопка «Из стандарта…» переносит функции выбранных функциональных блоков
внутрь прямоугольника ИЭУ вместе с сигналами, уставками и МЭК-именами.
Порты ИЭУ привязываются к клеммам (`mount_terminal`) и испытательным
блокам (`mount_test_block`, 4+1/6+1) линиями монтажной цепи. Панель
элементов переключается: «Первичная схема / Логическая схема /
Монтажная схема».

## Функционально-логическая схема в составе ИЭУ

В модели `EA/structure2.xml` функционально-логическая схема связана с ИЭУ
(`FunctionalLogicScheme`): «ФЛС отрисовывается в редакторе электрических
схем и может быть включена в состав ИЭУ структуры». Ссылка на схему —
строковое поле `scheme` у ИЭУ (и у `Figure` в документе): путь к JSON-файлу
редактора, обычно относительный от папки стандартов:

```json
{"number": 1, "description": "ШЭТ 431.11-1",
 "scheme": "schemes/флс-ШЭТ-431.11-1-1.json"}
```

Что с этой схемой можно делать:

* **панель ИЭУ** в редакторе стандарта (`ea_editor.py`): поле «Файл схемы»,
  кнопки «Выбрать…», «Создать из функций…» (генерация заготовки по блокам и
  функциям ИЭУ), «Открыть в редакторе…» (запуск редактора схем с файлом) и
  «Убрать»; под ними — живой предпросмотр схемы;
* **создание из функций** — `logic_scheme_render.scheme_from_ied(ied)`:
  каждый `FunctionBlock` становится функциональным блоком ФЛС, каждая
  `Function` — функцией со слотами; связи рисует пользователь;
* **рендер без редактора** — `logic_scheme_render.export_png_file(path,
  image)`: та же геометрия и подписи, что в экспорте редактора (номера у
  концов линий, наименования сигналов);
* **аналоговые цепи** (`analog_links` JSON) рисуются в отчёте так же, как при
  экспорте PDF/PNG: фиолетовый пунктир, стрелка к ТТ/ТН и подпись цепей
  напряжения/тока (`logic_scheme_render.draw_analog_links`);
* **DOCX** — рисунок, у которого заполнено `scheme`, вставляется в документ
  картинкой (`ea_docx._scheme_image`); остальные рисунки остаются подписью;
* **кнопка «Открыть в редакторе…»** запускает `main.py <файл схемы>` в
  отдельном процессе — редактор открывает схему сразу.

Панель рисунка (`Figure`) содержит то же поле «Файл схемы» с предпросмотром:
так в документ попадает отрисованное изображение ФЛС вместо пустой подписи.
В поле «Файл схемы» можно указать как JSON редактора ФЛС, так и готовое
изображение PNG/JPEG/BMP/GIF: оно вставляется в документ без рендера, а в
панели редактора стандарта показывается предпросмотр. Выбор файла и предпросмотр
поддерживают оба вида. Поля «Формат» (`A5`/`A4`/`A3`) и «Ориентация»
(«книжная»/«альбомная») позволяют вынести рисунок на отдельную страницу
нужного формата; пустые значения означают формат остального документа.
Картинка вписывается в доступную область страницы.

В DOCX подписи таблиц и рисунков получают закладки, а упоминания вида
«Таблица 5.2» / «Рисунок 4.1» в тексте (включая ячейки таблиц) превращаются
в поля `REF … \h`: ссылки кликабельны и обновляются в Word по F9. Суффикс
`/#/0` в упоминании (например, `Таблица 5.2/#/0` или `Рисунок 4.1/#/0`)
убирает метку: REF получает переключатель `\#"0"`, в документе остаётся
только номер (`5.2`, `4.1`), а сам суффикс из текста исчезает. Если у
таблицы заполнено поле «Ширина колонок» (`colums_width`, список миллиметров),
ширина колонок и всей таблицы фиксируется в XML; пустой список означает
автоматическую ширину по содержимому в пределах текущей страницы (страница
минус поля) — таблицы не выходят за ширину текста, в том числе в книжном
«Отчете по НИР».

**Двухуровневая шапка** таблицы задаётся в её строках флагами
`is_header_first_row` / `is_header_second_row`; `es.table_header_rows()`
возвращает один или два яруса. В DOCX оба яруса выводятся отдельными
строками, повторяются на новой странице (`w:tblHeader`) и объединяются:
одинаковые соседние подписи верхнего яруса — по горизонтали (`w:gridSpan`),
а подпись, повторённая во втором ярусе, — по вертикали (`w:vMerge`).
Ширина колонок считается по самой длинной ячейке каждого столбца, а узкие
колонки подтягиваются до минимума, чтобы «КТ», «ЦУС», «РДУ» не рвались по
буквам (`ea_docx._header_widths`, `_min_widths`, `_fit_minimums`). В окне
редактора шапка показывается одной строкой «верх / низ»: `Treeview` не
умеет объединять ячейки заголовка, но обе строки сохраняются в JSON.

Реквизит «Титульный лист (DOCX)» (`title_page`) задаёт готовый документ,
который открывает сборку. Путь может быть абсолютным или относительным
папки стандартов; кнопка «Выбрать…» в реквизитах подставляет относительный
путь. При выгрузке содержимое этого DOCX остаётся первым, а сгенерированный
отчёт добавляется после него новой секцией A4 книжной с полями 1,5 см;
встроенный титул не создаётся. Колонтитулы титула в отчёт не переносятся:
в верхнем колонтитуле новой секции стоит поле PAGE, поэтому нумерация
страниц продолжается от титула, а нижний колонтитул остаётся пустым.
Текст готового титула не переписывается перекрёстными ссылками.

## Исполняемая схема structure2

[`ea_schema.py`](ea_schema.py) — исполняемое описание модели
`EA/structure2.xml` без зависимости от Enterprise Architect. Для каждого из
35 классов заданы скалярные поля (в порядке атрибутов модели) и вложенные
коллекции. API:

* `fields(cls)` / `children(cls)` — описание полей и коллекций;
* `label(key)` — подпись поля в интерфейсе;
* `kind_of(cls, key)` / `child_class(cls, key)` — тип поля / класс элемента;
* `new_node(cls, **values)` — новый узел со всеми полями схемы;
* `normalize(cls, item)` — добавить отсутствующие поля, переименовать старые
  имена (`ALIASES`), привести типы, рекурсивно обойти коллекции;
* `normalize_document(data)` — то же для всего стандарта.

Мигратор (`tools/migrate_standards_structure2.py`) использует схему, чтобы
добавить в стандарты новые поля structure2: `IED.description`,
`Table.colums_width`, `TerminalRow.assembly_unit`. Лишние поля не удаляются —
в стандартах есть данные, используемые редактором (`Table.cabinet`,
`Cabinet.containers`, `Standard.functional_blocks` — `EXTRA_FIELDS`).
Дополнения редактора к structure2: `order` у блоков и пунктов (общий порядок)
и `Kit.identical` (группа взаимозаменяемых комплектов). `order` редактор
добавляет сам при переносе, а `Kit.identical` зарегистрировано в
`EXTRA_FIELDS`; мигратор эти поля не создаёт.
Повторный запуск ничего не меняет.

```bash
python tools/migrate_standards_structure2.py --check           # только отчёт
python tools/migrate_standards_structure2.py                   # применить
python tools/migrate_standards_structure2.py --add-children    # + пустые коллекции
```

|---|---|
| [`ea_standard.py`](ea_standard.py) | чтение папки, обход дерева, `table_view()` — сборка строк таблицы из шкафа, `table_header_rows()` — один или два яруса шапки, `cabinet_card()`, `validate()`, CLI |
| [`ea_schema.py`](ea_schema.py) | исполняемая схема structure2: поля, коллекции, псевдонимы, подписи и значения по умолчанию для всех классов модели; нормализация и фабрика узлов |
| [`ea_model.py`](ea_model.py) | модель structure2: блоки функций, слоты и их типы, уставки, параметры, нормализация и миграция |
| [`ea_ui.py`](ea_ui.py) | окно «СТО (EA)…»: дерево документа и шкафов, таблицы, карточки, размещение на схеме, новый стандарт, DOCX |
| [`ea_edit.py`](ea_edit.py) | обратимое представление таблиц: `load()` → шапка и строки, `save()` → обратно в `cabinets` |
| [`ea_structure.py`](ea_structure.py) | фабрики новых узлов, добавление/удаление (`new_*`, `add`, `remove`, `delete_issues`), перенос и копирование таблиц и рисунков (`move_node`, `move_block`, `copy_table`, `copy_figure`, `next_table_number`), общий порядок пунктов, подпунктов, таблиц и рисунков (`ordered_items`, `move_item`, `ordered_blocks`), привязка таблиц к шкафу (`rebind_table`, `rebind_tables`), группа идентичных комплектов и перенос/копия комплектов (`kit_feeds_tables`, `identical_replacement`, `promote_kit`, `move_kit`, `copy_kit`) |
| [`ea_editor.py`](ea_editor.py) | отдельное окно редактирования стандарта: текст, таблицы, карточки шкафов, комплекты, ИЭУ, блоки/функции/слоты/уставки/параметры, универсальная правка любого поля, контекстное меню дерева |
| [`ea_catalog.py`](ea_catalog.py) | мост «шкаф стандарта ↔ каталог редактора»: `ensure_catalog()`, `kit_entry()`, `cabinet_from_catalog()`, `kit_from_catalog()`, `add_test_blocks()` |
| [`ea_merge.py`](ea_merge.py) | каталог шкафов всех стандартов и слияние: `merge_cabinets()`, `add_catalog_cabinet()` |

| [`ea_docx.py`](ea_docx.py) | выгрузка стандарта в Word: титул, оглавление, разделы и таблицы из шкафов, жёсткая ширина колонок и двухуровневая шапка с объединением ячеек, рисунки со схемами ФЛС и их формат/ориентация, закладки и перекрестные ссылки |
| [`logic_scheme_render.py`](logic_scheme_render.py) | рендер ФЛС без редактора: сборка схемы из JSON, аналоговые цепи, PNG-экспорт, генерация заготовки из функций ИЭУ |
| [`main.py`](main.py) | кнопка «СТО (EA)…» на вкладке «Стандарты» и метод `show_ea_standards` |
| [`EA/docx2json.py`](EA/docx2json.py) | сборка JSON стандарта из DOCX по модели EA |
| [`tools/migrate_standards_structure2.py`](tools/migrate_standards_structure2.py) | перевод JSON стандартов на structure2: `function_blocks` и новые поля модели по `ea_schema.py` (`--check` — только отчёт, `--add-children` — пустые коллекции) |
| [`tests/test_ea_standard.py`](tests/test_ea_standard.py) | проверка данных, сборки таблиц, CLI и окна |
| [`tests/test_ea_features.py`](tests/test_ea_features.py) | размещение, новый стандарт, DOCX, архив, редактор таблиц, перенос типовых шкафов и комплектов, групповые перенос/копирование/удаление в дереве, общий порядок пунктов, подпунктов, таблиц и рисунков, дублирование узлов функциональной модели, схема structure2, произвольные поля редактора, идентичные комплекты и перепривязка таблиц, двухуровневая шапка таблиц в DOCX, схема ФЛС и аналоговые цепи в отчёте |

Папка стандартов: `EA/` рядом с исходниками, `db/EA/` в собранном
приложении (`apppaths.data_dir("EA")`).

## Запуск

```bash
python ea_standard.py --list                  # стандарты в папке
python ea_standard.py --stats                 # счётчики
python ea_standard.py --check                 # ссылки «таблица → шкаф», полнота сигналов
python ea_standard.py --table 5.3 --limit 10  # таблица, собранная из шкафа
python ea_standard.py --cabinet "ШЭТ 431.11-1"
python ea_catalog.py --check                  # шкафы стандарта в каталоге редактора
python ea_catalog.py --cabinet "ШЭТ 431.11-1"
python ea_new_standard.py --dry-run --code "СТО (проект, ред. 3)" --date 01.01.2027
python ea_new_standard.py --out "EA/new.json" --code "..." --date 01.01.2027 \
    --keep "ШЭТ 431.12-1" --replace "431.12-1 => 431.99-1"
python ea_docx.py --out "Отчет.docx"           # титул, оглавление, все таблицы
python tools/migrate_standards_structure2.py --check  # новые поля structure2
python tests/test_ea_standard.py --no-gui     # тесты без окна
```

В редакторе: вкладка **«Стандарты»** → **«СТО (EA)…»**. Слева дерево
разделов, шкафов, комплектов и ИЭУ, справа — таблица с данными из шкафа,
карточка шкафа или список функций ИЭУ.

* **«На схему»** (выбран шкаф) — шкаф заносится в каталог редактора
  (`ea_catalog.ensure_catalog`) и ставится на чертёж. Если запись с таким
  шифром уже есть, она используется как есть.
* **«Комплект → в шкаф»** (выбран комплект) — комплект добавляется в шкаф,
  выделенный на схеме (`add_komplekt_to_cabinet`).
* **«Реквизиты…»** — правка полей открытого стандарта (шифр, наименование,
  принадлежность, дата введения) с записью в его JSON.
* **«Редактор…»** — отдельное окно (`ea_editor.py`): дерево «реквизиты →
  документ → шкафы» слева, редактор узла справа. Правятся текст разделов и
  пунктов, строки всех таблиц (двойной щелчок по ячейке, добавление и
  удаление строк), карточка шкафа с вводами питания, комплекты и цифровые
  порты ИЭУ. У таблицы в дереве раскрываются её колонки — состав таблицы
  виден, не открывая сетку; выбор колонки показывает ту же таблицу.
  Правки копятся в памяти и пишутся в JSON по «Сохранить»
  (Ctrl+S); строки таблиц раскладываются по шкафам через `ea_edit`.
  **Правый клик по дереву** — контекстное меню: добавить раздел, подраздел,
  пункт, таблицу, рисунок, шкаф, комплект или ИЭУ; удалить выбранный узел.
  Диалог новой таблицы предлагает два варианта: таблица документа (строки
  хранятся в самой таблице, колонки задаются в диалоге) или таблица шкафа
  (выбор шкафа и вида данных из `es.KINDS`; имя содержит нужный фрагмент, а
  шапка берётся из `ea_edit`). Шкаф, на который ссылаются таблицы, и его
  первый ИЭУ удалить нельзя — редактор предупредит и укажет номера таблиц.
  Первый комплект такого шкафа тоже питает таблицы, но его можно удалить,
  если в группе «Идентичны» есть замена (см. ниже). Структурные операции
  реализованы в `ea_structure.py`.
  **Номер и наименование таблицы** правятся в полях над сеткой: номер
  проверяется на уникальность, ссылка «Таблица N» обновляется; у таблицы
  шкафа сменить вид данных в наименовании нельзя (форма не совпадёт со
  строками), а если в наименовании указан другой шифр, редактор подскажет
  привязать таблицу к нему. **Смена шифра шкафа** в его карточке сразу
  перепривязывает все таблицы этого шкафа и обновляет шифр в их
  наименованиях (`st.rebind_tables`), поэтому ссылки не теряются; занятый
  шифр редактор не примет.
  **«Привязать к другому шкафу…»** (правый клик по таблице шкафа) меняет
  ссылку `cabinet` и шифр в наименовании таблицы; форма и номер
  сохраняются, строки начинают собираться из нового шкафа. Если у нового
  шкафа нет данных такого вида, редактор предупредит, что таблица останется
  с одной шапкой. При удалении шкафа, на который ссылаются таблицы, редактор
  сам предлагает перепривязать их к другому шкафу (`st.rebind_tables`) —
  после этого шкаф удаляется.
  **Комплекты: группа «Идентичны», перенос и копия.** Таблицы шкафа
  собираются из первого комплекта (`st.kit_feeds_tables`), поэтому раньше
  его нельзя было удалить. Поле **«Идентичны (группа)»** в карточке
  комплекта помечает взаимозаменяемые комплекты: если удалить питающий
  таблицы комплект, а в той же непустой группе есть другой, редактор сам
  ставит его первым и связи с таблицами сохраняются
  (`st.identical_replacement`, `st.promote_kit`). Если замена нашлась в
  другом шкафу, таблицы дополнительно перепривязываются к нему
  (`st.rebind_tables`). **«Переместить в другой шкаф…»** переносит комплект
  (`st.move_kit`): при переносе первого комплекта редактор спрашивает,
  перепривязать ли таблицы к новому шкафу, либо оставить их на исходном,
  если там есть идентичный комплект. **«Дублировать комплект»** создаёт
  копию рядом (`st.copy_kit`), сохраняя номер по порядку и группу
  «Идентичны»; скопированный комплекс тоже может заменить оригинал.
  **Выделение группы** (Ctrl+щелчок или Shift+щелчок в дереве) даёт меню
  «Привязать выделенное к другому шкафу…» (только таблицы), «Переместить
  выделенное…», «Копировать выделенное…» и «Удалить выделенное»; клавиша
  Delete удаляет выделение. Группой переносятся и копируются таблицы и
  рисунки: таблицы получают номера по целевому разделу, рисунки — следующий
  номер, копии выделяются в дереве. При удалении группы узлы внутри уже
  выделенного родителя отдельно не запрашиваются, а запреты `delete_issues`
  проверяются для всех сразу.
  **Общий порядок пунктов, таблиц и рисунков**: перетаскивание ставит пункт
  над таблицей или рисунком, а таблицу и рисунок — над пунктом и друг над
  другом. Подпункты так же переносятся внутри пункта. При первом таком
  переносе элементы контейнера получают поле `order` (дополнение редактора
  к structure2), списки `clauses`, `subclauses`, `tables` и `figures`
  переписываются в общем порядке, и этот же порядок используют дерево
  редактора и выгрузка DOCX (`st.ordered_items`, `st.move_item`). В
  документах без `order` сохраняется прежний порядок: сначала таблицы,
  затем рисунки, затем пункты и подпункты.
  **Функциональная модель ИЭУ** доступна в дереве редактора: блоки функций,
  функции, входы/выходы, уставки и параметры. Контекстное меню добавляет блок
  (правый клик по ИЭУ), функцию (по блоку), слот/уставку/параметр (по функции)
  и удаляет их. Поля и коллекции новых узлов создаются по схеме `ea_schema.py`.
  **«Дублировать …»** вставляет копию выбранного узла сразу после оригинала:
  имя получает пометку «(копия)» (повторно — «(копия 2)»), вложенные функции,
  слоты, уставки и параметры копируются целиком, у входа/выхода обновляется
  `id`. Те же действия доступны по Ctrl+D и Ctrl+C / Ctrl+V.
  **Произвольные поля любого узла** правятся в универсальной панели под
  специализированной: список показывает все поля узла с подписями из схемы,
  кнопки «Изменить…», «Добавить поле…» и «Удалить поле» меняют их состав.
  Введённые значения приводятся к типу существующего поля (числа, логические
  значения), для новых полей — по правилу числа. Специализированные панели
  (текст, таблица, шкаф, комплект, ИЭУ) остаются, универсальная панель
  дополняет их и работает с любым классом модели.
* **«Добавить типовой шкаф из каталога…»** (правый клик по узлу «Шкафы») —
  шкаф каталога редактора переносится в стандарт вместе с данными:
  карточкой, вводами питания, комплектами, ИЭУ, функциями, аналоговыми
  измерениями, дискретными цепями, GOOSE и испытательными блоками. Для
  всех видов данных создаётся подраздел с таблицами-формами, поэтому шкаф
  сразу виден в документе. Преобразование — `ea_catalog.cabinet_from_catalog`,
  добавление — `ea_merge.add_catalog_cabinet`.
* **«Добавить типовой комплект из каталога…»** (правый клик по шкафу) —
  в комплект переносятся ИЭУ, функции и аналоговые измерения, а
  испытательные блоки дополняют таблицу компонентов шкафа
  (`ea_catalog.kit_from_catalog`, `ea_catalog.add_test_blocks`).
* **«Новый стандарт…»** — диалог: реквизиты, набор шкафов, замены,
  перенумерация. Кнопка **«Из каталога…»** добавляет в набор типовые шкафы
  каталога (в том числе отсутствующие в файлах стандартов); они
  переносятся с данными и таблицами-формами, как в редакторе. Результат —
  отдельный JSON в папке стандартов.
* **«DOCX…»** — сборка документа Word в фоне (таблицы берутся из шкафов).
* **«Проверить»** — `ea_standard.validate()`.

## Что не зависит от старой ветки

`ea_standard.py` импортирует только стандартную библиотеку и `apppaths`.
`ea_ui.py` добавляет `ui_theme`, `ea_catalog` (каталог шкафов `cabs` и
`komplekts`), `ea_merge`, `ea_editor`, `ea_new_standard` и `ea_docx`. Старой ветки —
`standards_base`, `standards_editor`, `standards_ui`, `standard_editor` — не
использует ни один из них, поэтому новую ветку можно развивать, не
оглядываясь на старую.

## Поддержка контейнеров

Поле `containers` в карточке шкафа (`ea_standard.py`) — массив id контейнеров КЭТ,
в которые входит шкаф. Оно используется в `ea_standard.record()` для формирования
записи `structure.json` v3, где шкафы содержат массив `контейнеры` с обратными
ссылками на КЭТ.

Поле заполняется автоматически при сборке стандарта из шкафа: если у шкафа в JSON
есть `containers`, они копируются в запись v3. При необходимости можно добавлять
контейнеры в карточку шкафа вручную или через `ea_catalog.ensure_catalog()`.
