# rza_catalog — нормализованная модель каталога РЗА

Пакет перекладывает «плоский» пользовательский каталог из
`cabinets.json` (`custom` / `overrides` / `deleted`) в явную иерархию:

```
Container (КЭТ / контейнер)
  └── Cabinet (шкаф)
        └── Kit (комплект)
              └── Ied (ИЭУ)
```

Исходные `komplets` шкафа — это смесь шкафов и комплектов. Комплекты
группируются по `cabinet_key`; если ключа нет, запись становится
самостоятельным inline-шкафом (так приходят `draft-*`).

## Запуск

```bash
python3 migrate_catalog.py                   # cabinets.json → output/
python3 -m rza_catalog                       # то же через пакет
python3 migrate_catalog.py путь/к/файлу.json # другой источник
python3 migrate_catalog.py --no-sqlite       # только JSON
python3 migrate_catalog.py --strict          # падать на повторах ключей
```

`migrate_catalog.py` — тонкая обёртка: в репозитории уже есть `main.py`
приложения, поэтому CLI пакета вызывается через неё.

По умолчанию пишутся:

* `output/catalog.normalized.json` — нормализованный JSON;
* `output/catalog.sqlite` — та же модель в реляционном виде.

Оба файла пишутся атомарно, через временный файл. Каталог `output/`
уже исключён из git.

Текущий прогон CLI на `cabinets.json`:

```
Контейнеров:        33
Шкафов:             37
Комплектов:         46 (с ИЭУ: 46)
ИЭУ:                46
Функций:            140
Стандартов:         4
Испытательных блоков: 63
Удалённых ключей:   6
```

33 контейнера = 32 записи `custom` + 1 `override`
(`shet-610-01-1`). Шесть ключей из `deleted` относятся к встроенному
каталогу, поэтому на число пользовательских контейнеров не влияют.

Рабочее хранилище приложения `catalog.normalized.json` содержит:
282 встроенных шкафа, 16 встроенных КЭТ, 33 пользовательские записи
шкафов и 1 пользовательский КЭТ. Встроенные данные перенесены в разделы
`builtin_cabinets` / `builtin_kets`; модули `cabs_data.py`,
`cabs_sto.py` и статический список `containers.py` оставлены только
резервным источником.

## Формат JSON

```json
{
  "schema_version": 2,
  "builtin_cabinets": ["..."],
  "builtin_kets": ["..."],
  "containers": [
    {
      "id": "...",
      "key": "...",
      "cabinets": [
        {
          "id": "...",
          "key": "...",
          "kits": [
            {
              "id": "...",
              "cabinet_id": "...",
              "ieds": [
                {"id": "...", "kit_id": "...", "name": "ИЭУ1", "type": "МП РЗА"}
              ],
              "test_blocks": {
                "voltage": {"count": 2, "circuits": ["Ua", "Ub"]},
                "current": {"count": 1, "circuits": ["Ia"]},
                "blocks": [
                  {"name": "SG1", "circuits": "Ia", "count": "6+1",
                   "note": "..."}
                ]
              },
              "io_in": [
                {"name": "Пуск", "code": "PTRC.Str", "details": "..."}
              ],
              "io_out": [
                {"name": "Отключить", "code": "PTRC.Op", "details": "..."}
              ]
            }
          ]
        }
      ]
    }
  ],
  "deleted": ["..."],
  "standards": {"...": {"key": "...", "title": "...", "edition": "..."}},
  "functions": {"...": {"code": "...", "title": null}}
}
```

`id` и `key` у контейнера совпадают. У шкафа `key` — исходный
`cabinet_key`, `id` — уникальный идентификатор в пределах каталога
(при коллизии добавляется суффикс). У комплекта и ИЭУ `id` уникален,
а `cabinet_id` / `kit_id` — обратные ссылки для плоских выборок.

## Что важно знать о преобразованиях

* **Обрывки функций склеиваются.** `["СЗ ВН (ДЗ", "ТНЗНП", "МТЗ",
  "ОУ", "АУ", "БНН", "БК)"]` → `["СЗ ВН (ДЗ, ТНЗНП, МТЗ, ОУ, АУ, БНН,
  БК)"]`. Склейка идёт до нулевого баланса скобок. Незакрытый хвост не
  выбрасывается.
* **`test_blocks` и `test_block_list` унифицируются.** Группы
  напряжения/тока попадают в `TestBlocks.voltage/current`, построчный
  перечень — в `TestBlocks.blocks`. Точные повторы строк убираются.
* **`overrides` накладываются рекурсивно.** Словари сливаются, списки
  (включая `komplets`) заменяются. Поля, которых нет в override,
  сохраняются из `custom`.
* **`deleted` применяется последним** и попадает в итоговый список
  `deleted`.
* **`extensions` сохраняют всё, что не стало явным полем**: описательные
  поля СТО (`mp_functions`, `ports`, …), `size`, `composition` и т. п.
  Пустые значения и `null` в extensions не тащатся.
* **`has_ied` и `source` комплекта** вынесены в явные поля, чтобы не
  терять данные исходного формата.
* **Сигналы комплекта** (`io_in`, `io_out`, `goose_in`, `goose_out`)
  хранятся как список строк «наименование, код МЭК 61850, сведения».
  Для одно-комплектных шкафов они подставляются из собранных
  `cabs_signals.json`; для многокомплектных шкафов источник задаёт
  сигналы на шкаф, поэтому их нужно завести/отредактировать на уровне
  комплекта вручную.
* **`standard` может быть строкой-подписью** («СТО (проект, ред. 2)»).
  Она сохраняется в `StandardRef.label`, полное наименование — в
  `title`.
* **Повторяющиеся ключи** в `custom` по умолчанию переименовываются с
  суффиксом `:dupN` и дают предупреждение; в `--strict` — исключение.
* **Нормализованный JSON можно прочитать обратно** тем же
  `load_catalog`: `containers` распознаётся как готовая модель,
  `cabinets` — как список объектов, а не `komplets`.

## Интеграция с приложением

Рабочее хранилище приложения — `catalog.normalized.json` в корне
репозитория. Модуль `store.py`:

* читает и атомарно пишет этот файл;
* при первом запуске собирает его из старых `cabinets.json` /
  `containers.json` / `komplekts.json`, если файла ещё нет;
* отдаёт `cabs.py`, `containers.py` и `komplekts.py` привычные словари,
  поэтому интерфейс редактора не пришлось переписывать.

Типы записей:

* `entry_type = "builtin_cabinet"` / `"builtin_ket"` — встроенные шкафы
  и КЭТ, перенесённые из кода;
* `entry_type = "cabinet"` — пользовательская запись каталога шкафов;
* `entry_type = "ket"` — пользовательский КЭТ со ссылками на шкафы
  (`extensions.cabinet_keys`);
* `entry_type = "kit_catalog"` — служебный контейнер для пользовательских
  комплектов и правок типовых комплектов.

Встроенные 282 шкафа лежат в `builtin_cabinets`, 16 КЭТ — в
`builtin_kets`. Пользовательские шкафы, КЭТ и комплекты пишутся в
`containers`. Старые `cabinets.json`, `containers.json` и
`komplekts.json` приложением больше не читаются (только однократный
bootstrap при отсутствии нового файла). Если `catalog.normalized.json`
отсутствует или в нём нет встроенных разделов, `cabs.py` /
`containers.py` откатываются к данным из кода.

Сброс каталогов раздельный: сброс шкафов не удаляет пользовательские
КЭТ и комплекты, сброс КЭТ не удаляет шкафы, сброс комплектов не трогает
ни то, ни другое.

## Классовый (доменный) подход

Модуль `domain.py` — классы с полями для работы с данными как с объектами,
а не со словарями:

```
Kit          — комплект: ИЭУ (has_ied / ieds — «с ИЭУ» / «без ИЭУ»),
               входные цепи (io_in, goose_in, analog_inputs) и
               выходные цепи (io_out, goose_out), испытательные блоки
               (test_blocks: группы U/I и построчный перечень БИ),
               функции, теги, описание, описательные поля СТО (details),
               всё остальное — extensions
Cabinet      — шкаф: набирается из комплектов (kits), ключ шкафа — ключ
               его записи каталога; тип вычисляется по комплектам
               (типовой, только если все комплекты типовые)
Container    — контейнер КЭТ: содержит шкафы (cabinets), набирается по
               cabinet_keys из библиотеки шкафов, хранит слоты, типоразмер
               и состав; умеет генерить отчёт
Ied, SignalEntry, AnalogInput, TestBlocks, CircuitGroup, TestBlockEntry
DomainCatalog — корневой объект: библиотеки kits / cabinets / containers
```

У каждого класса есть `to_dict()` / `from_dict()` (принимает словари
приложения: `desc`→`description`, `test_block_list`→`test_blocks.blocks`,
`cabinet_key`→`cabinet_id`, функции-объекты→коды) и `to_model()` /
`from_model()` — конвертация в нормализованную модель хранения `models.py`.
Ключ комплекта в библиотеке — тот же, что у каталога комплектов:
`typ:<ключ шкафа>:<номер>` / `cab:<ключ шкафа>:<номер>` (`Kit.app_key()`).

Заполнение классов из базы — `DomainCatalog.load()` (читает
`catalog.normalized.json` через `store.py`):

```python
from rza_catalog.domain import DomainCatalog
catalog = DomainCatalog.load()      # Kits/Cabinets/Containers из хранилища
catalog.kits        # библиотека комплектов (339)
catalog.cabinets    # шкафы (308), kits — общие экземпляры библиотеки
catalog.containers  # КЭТ (17), cabinets — ссылки на библиотеку шкафов
```

Повторяется семантика приложения: пользовательская правка шкафа (override)
заменяет встроенный шкаф тем же ключом; удалённые шкафы и КЭТ
(`deleted` / `deleted_containers`) не заполняются; правки и пользовательские
комплекты из каталога комплектов накладываются на библиотеку
(`overrides` по ключу, `custom` добавляются, `deleted` снимаются); сигналы
СТО для одно-комплектных шкафов подтягиваются из `cabs_signals.json`.
Объекты в рамках одного `DomainCatalog` разделяются: один и тот же Kit
лежит в шкафу и в библиотеке комплектов, один Cabinet — в каталоге шкафов
и во всех ссылающихся на него КЭТ. Ссылочная целостность проверяется
тестами (`test_cabinets_share_library_kits`, `test_kit_keys_match_app`).

Отчёт генерит сам контейнер — формат совместим с
`docxreport.build_selection_report`:

```python
ket = catalog.container("ket-6-1-ii")
report = ket.report_data()            # словарь отчёта (тот же, что у редактора)
ket.write_report("отчёт.docx")        # DOCX без внешних зависимостей
```

В редакторе (`main.py`) кнопка «Отчёт…» в каталоге КЭТ сначала пробует
доменный отчёт (`_domain_container_report`), при недоступности доменного
слоя использует прежний сборщик из словарей.

CLI:

```bash
python3 domain_catalog.py                       # сводка по базе
python3 domain_catalog.py --list                # перечень контейнеров
python3 domain_catalog.py --dump output/domain.json   # переносимый дамп
python3 domain_catalog.py --report ket-6-1-ii --out otchet.docx
python3 -m rza_catalog.domain ...               # то же через модуль пакета
```

Дамп `domain.json` хранит данные без дублирования: `kits` — полные
комплекты, `cabinets` — шкафы со своими комплектами, `containers` — КЭТ со
ссылками на шкафы (читается `DomainCatalog.from_dump()`, объекты снова
общие).

## Сценарий: комплект → шкаф → контейнер → отчёт

1. **Комплекты** ведутся отдельно в каталоге комплектов. Типовой комплект
   можно создать без шкафа-источника (из собранных СТО и документов) или
   отредактировать. У комплекта есть:
   * признак «есть ИЭУ» и список ИЭУ;
   * входные и выходные сигналы (`io_in`, `io_out`) в формате
     «наименование | код МЭК 61850 | сведения»;
   * аналоговые измерения, испытательные блоки, функции, теги и
     описательные поля СТО.
2. **Шкаф** собирается из комплектов в редакторе шкафа: кнопка
   «+ Из каталога…» добавляет комплект из каталога, «Обновить из
   каталога» подтягивает изменённые данные комплектов в уже собранный
   шкаф. Вид шкафа вычисляется по комплектам: типовой — только если все
   комплекты типовые; если хотя бы один нетиповой, шкаф нетиповой.
3. **Контейнер** собирается из шкафов в редакторе КЭТ (слоты контейнера).
4. **Отчёт Word** по контейнеру: в каталоге КЭТ выберите контейнер и
   нажмите «Отчёт…». Документ содержит общие сведения, таблицу шкафов с
   типом, комплекты с ИЭУ, сигналами, аналоговыми измерениями и
   испытательными блоками; сохраняется в `.docx`.

## SQLite

Схема повторяет иерархию и добавляет плоские справочники/связи:

| Таблица | Назначение |
|---|---|
| `containers` | контейнеры, `standard_key` → `standards` |
| `cabinets` | шкафы, `container_id` → `containers` |
| `kits` | комплекты, `cabinet_id` → `cabinets` |
| `ieds` | ИЭУ, `kit_id` → `kits` |
| `functions` | справочник функций |
| `container_functions`, `kit_functions` | связи функций с контейнером/комплектом |
| `container_controlled` | управляемые выключатели |
| `container_tags`, `kit_tags` | метки |
| `kit_signals` | входные/выходные сигналы и GOOSE комплектов |
| `test_blocks` | группы напряжения/тока и построчные блоки |
| `test_block_circuits` | точные списки цепей (не «склеенная» строка) |
| `analog_inputs` | аналоговые входы |
| `deleted` | удалённые ключи |
| `catalog_meta` | `schema_version` |

Внешние ключи включены; после записи выполняется
`PRAGMA foreign_key_check`. Повторный экспорт в тот же файл безопасен:
таблицы пересоздаются, запись идёт через временный файл.

SQLite-выгрузка CLI описывает пользовательский каталог
(`containers`). Встроенные разделы `builtin_cabinets` / `builtin_kets`
остаются в JSON и в приложении, в SQLite не дублируются.

## Ограничения

* Встроенные справочники перенесены в `catalog.normalized.json`, но
  `cabs_data.py`, `cabs_sto.py` и статический список в `containers.py`
  оставлены как резервный источник. При наличии встроенных разделов в
  JSON приложение использует JSON.
* Старые `cabinets.json`, `containers.json`, `komplekts.json` оставлены
  как источник для первого bootstrap. После появления
  `catalog.normalized.json` приложение их не читает.
* Схема `schema_version = 2`; при несовместимом изменении модели
  потребуется миграция самого хранилища.

## Файлы

* `models.py` — dataclass-модель;
* `migrate.py` — парсер, склейка функций, унификация блоков, слияние
  `custom` + `overrides` + `deleted`;
* `export.py` — нормализованный JSON;
* `to_sqlite.py` — SQLite;
* `store.py` — хранилище приложения и адаптеры к словарям
  `cabs.py` / `containers.py` / `komplekts.py`;
* `main.py` — CLI пакета;
* `../migrate_catalog.py` — точка входа из корня репозитория;
* `../catalog.normalized.json` — рабочее хранилище приложения.

## Тесты

```bash
python3 -m unittest discover -s tests -v
```

Покрыты склейка функций, группировка шкафов, override/deleted,
round-trip JSON → модель → JSON, уникальность id, SQLite и внешние
ключи, а также интеграция хранилища с каталогами приложения: сохранение,
удаление, раздельный сброс шкафов/КЭТ/комплектов.
