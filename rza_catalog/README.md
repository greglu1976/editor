# rza_catalog — нормализованная модель каталога РЗА

Пакет перекладывает «плоский» пользовательский каталог из
`cabinets.json` (`custom` / `overrides` / `deleted`) в явную иерархию:

```
Container (КЭТ / контейнер)
  └── Cabinet (шкаф)
        └── Kit (комплект)
              └── Ied (ИЭУ)
```

Исходные `komplets` шкафа — это смесь шкафов и комплектов. Комплекты
группируются по `cabinet_key`; если ключа нет, запись становится
самостоятельным inline-шкафом (так приходят `draft-*`).

## Запуск

```bash
python3 migrate_catalog.py                   # cabinets.json → output/
python3 -m rza_catalog                       # то же через пакет
python3 migrate_catalog.py путь/к/файлу.json # другой источник
python3 migrate_catalog.py --no-sqlite       # только JSON
python3 migrate_catalog.py --strict          # падать на повторах ключей
```

`migrate_catalog.py` — тонкая обёртка: в репозитории уже есть `main.py`
приложения, поэтому CLI пакета вызывается через неё.

По умолчанию пишутся:

* `output/catalog.normalized.json` — нормализованный JSON;
* `output/catalog.sqlite` — та же модель в реляционном виде.

Оба файла пишутся атомарно, через временный файл. Каталог `output/`
уже исключён из git.

Текущий прогон на `cabinets.json`:

```
Контейнеров:        33
Шкафов:             37
Комплектов:         46 (с ИЭУ: 46)
ИЭУ:                46
Функций:            140
Стандартов:         4
Испытательных блоков: 63
Удалённых ключей:   6
```

33 контейнера = 32 записи `custom` + 1 `override`
(`shet-610-01-1`). Шесть ключей из `deleted` относятся к встроенному
каталогу, поэтому на число пользовательских контейнеров не влияют.

## Формат JSON

```json
{
  "schema_version": 1,
  "containers": [
    {
      "id": "...",
      "key": "...",
      "cabinets": [
        {
          "id": "...",
          "key": "...",
          "kits": [
            {
              "id": "...",
              "cabinet_id": "...",
              "ieds": [
                {"id": "...", "kit_id": "...", "name": "ИЭУ1", "type": "МП РЗА"}
              ],
              "test_blocks": {
                "voltage": {"count": 2, "circuits": ["Ua", "Ub"]},
                "current": {"count": 1, "circuits": ["Ia"]},
                "blocks": [
                  {"name": "SG1", "circuits": "Ia", "count": "6+1",
                   "note": "..."}
                ]
              }
            }
          ]
        }
      ]
    }
  ],
  "deleted": ["..."],
  "standards": {"...": {"key": "...", "title": "...", "edition": "..."}},
  "functions": {"...": {"code": "...", "title": null}}
}
```

`id` и `key` у контейнера совпадают. У шкафа `key` — исходный
`cabinet_key`, `id` — уникальный идентификатор в пределах каталога
(при коллизии добавляется суффикс). У комплекта и ИЭУ `id` уникален,
а `cabinet_id` / `kit_id` — обратные ссылки для плоских выборок.

## Что важно знать о преобразованиях

* **Обрывки функций склеиваются.** `["СЗ ВН (ДЗ", "ТНЗНП", "МТЗ",
  "ОУ", "АУ", "БНН", "БК)"]` → `["СЗ ВН (ДЗ, ТНЗНП, МТЗ, ОУ, АУ, БНН,
  БК)"]`. Склейка идёт до нулевого баланса скобок. Незакрытый хвост не
  выбрасывается.
* **`test_blocks` и `test_block_list` унифицируются.** Группы
  напряжения/тока попадают в `TestBlocks.voltage/current`, построчный
  перечень — в `TestBlocks.blocks`. Точные повторы строк убираются.
* **`overrides` накладываются рекурсивно.** Словари сливаются, списки
  (включая `komplets`) заменяются. Поля, которых нет в override,
  сохраняются из `custom`.
* **`deleted` применяется последним** и попадает в итоговый список
  `deleted`.
* **`extensions` сохраняют всё, что не стало явным полем**: описательные
  поля СТО (`mp_functions`, `ports`, …), `size`, `composition` и т. п.
  Пустые значения и `null` в extensions не тащатся.
* **`has_ied` и `source` комплекта** вынесены в явные поля, чтобы не
  терять данные исходного формата.
* **`standard` может быть строкой-подписью** («СТО (проект, ред. 2)»).
  Она сохраняется в `StandardRef.label`, полное наименование — в
  `title`.
* **Повторяющиеся ключи** в `custom` по умолчанию переименовываются с
  суффиксом `:dupN` и дают предупреждение; в `--strict` — исключение.
* **Нормализованный JSON можно прочитать обратно** тем же
  `load_catalog`: `containers` распознаётся как готовая модель,
  `cabinets` — как список объектов, а не `komplets`.

## SQLite

Схема повторяет иерархию и добавляет плоские справочники/связи:

| Таблица | Назначение |
|---|---|
| `containers` | контейнеры, `standard_key` → `standards` |
| `cabinets` | шкафы, `container_id` → `containers` |
| `kits` | комплекты, `cabinet_id` → `cabinets` |
| `ieds` | ИЭУ, `kit_id` → `kits` |
| `functions` | справочник функций |
| `container_functions`, `kit_functions` | связи функций с контейнером/комплектом |
| `container_controlled` | управляемые выключатели |
| `container_tags`, `kit_tags` | метки |
| `test_blocks` | группы напряжения/тока и построчные блоки |
| `test_block_circuits` | точные списки цепей (не «склеенная» строка) |
| `analog_inputs` | аналоговые входы |
| `deleted` | удалённые ключи |
| `catalog_meta` | `schema_version` |

Внешние ключи включены; после записи выполняется
`PRAGMA foreign_key_check`. Повторный экспорт в тот же файл безопасен:
таблицы пересоздаются, запись идёт через временный файл.

## Ограничения

* Мигрируется **пользовательский** каталог из `cabinets.json`.
  Встроенные шкафы из `cabs_data.py` / `cabs_sto.py` в него не входят.
* `containers.json` (каталог КЭТ со ссылками на шкафы) можно подать на
  вход, но его `cabinets` — это список ключей, а не объекты. Ключи
  сохраняются в `extensions.cabinet_keys`, однако шкафы по ним не
  подтягиваются: для этого нужна отдельная операция соединения двух
  каталогов.
* Пакет не меняет `cabs.py`, `containers.py` и редактор схем. Это
  миграция/представление данных, а не замена текущего рантайма.

## Файлы

* `models.py` — dataclass-модель;
* `migrate.py` — парсер, склейка функций, унификация блоков, слияние
  `custom` + `overrides` + `deleted`;
* `export.py` — нормализованный JSON;
* `to_sqlite.py` — SQLite;
* `main.py` — CLI пакета;
* `../migrate_catalog.py` — точка входа из корня репозитория.

Покрыты склейка функций, группировка шкафов, override/deleted,
round-trip JSON → модель → JSON, уникальность id, SQLite и внешние
ключи.
