## Версионированные изменения стандарта (базовый JSON + патчи)

- Вопрос пользователя: как оформлять изменения (базовый JSON + один/несколько JSON с версиями), метки `NEW`/`DEPRECATED`/`OVERRIDE` к ключам. **Решение: метки — это коды операций в отдельном файле-патче, а не префиксы ключей.** Причины: префиксы загрязняют данные и ломают форму example.json / json_to_docx, не выражают удаление и частичное изменение строки, не несут версию/дату/основание, дают неоднозначный merge двух изменений и конфликтуют с порядком ключей.
- Формат `СТО-изменения/1.0` (`apply_changes.py`): поля `Идентификатор`, `Версия`, `Дата`, `Порядок`, `Статус`, `Основание`, `Применимо к` (`Шифр стандарта` + `SHA-256 базы`), `Заменяет`, `Изменения` (массив операций). Операции: `OVERRIDE` (`Значение` / `Поля` + `Было`), `NEW` (`Ключ`+`Значение`, `Перед`, `Позиция`), `DEPRECATED` (оставляет объект, добавляет `Статус`/`Основание`/`Действует до`/`Изменение`), `DELETE` (физически, `Перенумеровать`), `RENAME`.
- Адресация: `Путь` — массив сегментов; строки/шкафы находятся по бизнес-ключам через `{"@where": {...}}` (короткая форма `{"№":"17"}`), а не по индексам массива. Ключевое техническое решение: **канонический путь** (с селекторами, для журнала и поиска конфликтов) и **физический путь** (реальные ключи/индексы, для сверки diff с базой) — разные; без этого проверка «не изменилось ли лишнего» даёт ложные срабатывания на строках таблиц.
- Правила сборки: несколько файлов с одним `Идентификатор` = версии одного изменения, берётся старшая `Версия`; неактивный `Статус` пропускается; порядок (`Порядок`, `Дата`, `Идентификатор`); конфликт двух изменений на одном пути → ошибка, если нет `Заменяет` или `Разрешить`: true; `Было` проверяется в момент применения (после предыдущих патчей); `SHA-256 базы` защищает от чужой базы. После сборки пересчёт `Количество строк`, проверка нумерации 1..N, имён комплектов, ссылок, PUA, пустых таблиц и **сверка diff: все изменения обязаны лежать внутри задекларированных путей**.
- Результат содержит блок `Редакция` (применённые/исключённые изменения, отменённые элементы, хэш базы). `json_to_docx.py` доработан: рисует раздел «Сведения о редакции» и автоматически добавляет столбцы `Статус`/`Основание`/`Изменение`/`Действует до` в таблицы с отменёнными строками. `table_records` теперь подхватывает служебные поля строк.
- Демо: `changes/ИЗМ-1.json` (v1), `changes/ИЗМ-1_ред2.json` (v2, вытесняет v1), `changes/ИЗМ-2.json` (`Заменяет: ИЗМ-1`, добавляет `Комплект 3` без ИЭУ, удаляет строку с перенумерацией), `changes/ИЗМ-3.json` (статус «отменено» → пропущен). Сборка `_parse/demo_279_с_изм.json` + отчёт `_parse/changes_report.txt` + DOCX `_parse/demo_279_с_изм.docx` (190 КБ). 7 операций, 2 изменения, 2 исключённых файла, 1 отменённый элемент; 101 таблица сохранена; JSON детерминирован (SHA `c2c65b27…` при двух прогонах).
- Негативные тесты (`_parse/neg/`): конфликт без `Заменяет`, устаревшее `Было`, неверный хэш базы — все корректно завершаются с кодом 1 и понятным сообщением. `--strict` требует `Было` и считает предупреждения ошибками; `--dry-run` не пишет результат; `--fingerprint` печатает хэш базы для заполнения патча.
- Открытые вопросы политики (пользователь ещё не решил): служебные поля `Статус` внутри строк против отдельного sidecar-файла; автоматическая перенумерация 1..N против буквенных номеров `17а`; печатать ли отменённые строки в официальном отчёте или только в приложении изменений.

## Текстовый редактор изменений (после правки «текстовый конечно же редактор нужен!»)

- Пользователь сначала написал «нужен графический редактор», сразу исправил на **текстовый**. Решение: НЕ GUI, а компактный текстовый DSL `*.изм.txt` + CLI, который проверяет пути по базовому JSON и компилирует в канонический `СТО-изменения/1.0`.
- `changes_editor.py` — 7 команд: `init` (шаблон с автоподстановкой шифра и SHA-256 базы), `edit` (открыть в `--editor` / `STO_EDITOR` / `VISUAL` / `EDITOR` / VS Code `code --wait` / Блокнот, затем check+build+preview), `check`, `build`, `from-json`, `get`, `preview` (`--out` пишет собранную редакцию, `--strict`, `--ignore-hash`, `--report`).
- Формат: шапка (`ИЗМЕНЕНИЕ/ВЕРСИЯ/ДАТА/ПОРЯДОК/СТАТУС/НАЗВАНИЕ/ОСНОВАНИЕ/БАЗА/ХЭШ/ЗАМЕНЯЕТ`) + блоки операций. Глаголы `ЗАМЕНИТЬ`, `ИЗМЕНИТЬ ПОЛЯ`, `ДОБАВИТЬ`, `ОТМЕНИТЬ`, `УДАЛИТЬ`, `ПЕРЕИМЕНОВАТЬ` (и английские синонимы) → `OVERRIDE/NEW/DEPRECATED/DELETE/RENAME`. Путь: `шкаф=…`, `№=…`, `@Поле=…`, `@{json}`, `#3`, `"ключ / с косой"`; без ведущего `/` — от `Содержимое стандарта`. Поля `БЫЛО:`, `БЫЛО.Поле:`, `СТАЛО:`, `> ключ: значение`, `КЛЮЧ:`, `ПЕРЕНУМЕРОВАТЬ:`, `РАЗРЕШИТЬ:` и др. Значения `[…]`/`{…}` читаются как JSON.
- Технические решения: `compile_text()` собирает ключи в каноническом порядке (`CS_ORDER`/`OP_ORDER`), поэтому текст → JSON детерминирован; `decompile()` не пишет пустые/отсутствующие поля шапки (иначе `ХЭШ: ` порождал лишний `SHA-256 базы: ""`); `OVERRIDE` со словарным `Значение` рендерится как `СТАЛО:` (а не `> поля`), чтобы не превратиться в `Поля`. `check_paths()` НЕ проверяет `Было` (оно относится к состоянию после предыдущих патчей) и применяет операции на общей копии базы в порядке сборки — поэтому путь, созданный `NEW` в одном файле, виден в следующем. Ошибки `preview` переадресуются с temporаry `*.json` на исходный `*.изм.txt`.
- Проверки: 4 примера `changes/*.json` → `changes_text/*.изм.txt` → `changes_text/json/*.json` дают **семантически идентичный JSON** (`==`); текст → JSON → текст идемпотентен побайтно; `check --base` проходит; негативные тесты (`_parse/neg_text/`) ловят несуществующий ключ/шкаф/строку `№=999`, неизвестный глагол, `ДОБАВИТЬ` без `КЛЮЧ`, `ЗАМЕНИТЬ` без `СТАЛО`, неверный хэш базы — exit 1 с понятным текстом; позитивный тест на цепочку NEW→OVERRIDE проходит.
- Сквозная цепочка: `preview --strict --out` → `_parse/demo_279_из_текста.json`,содержимое стандарта (без блока `Редакция`) **полностью идентично** с `_parse/demo_279_с_изм.json` (различаются только `Редакция/Применённые изменения[].SHA-256 файла` и имена исключённых файлов — это и есть корректная проверка происхождения). Сборка детерминированна (SHA `af5a6987…` при двух прогонах). DOCX `_parse/demo_279_из_текста.docx` (190 КБ, 132 таблицы, TOC/PAGE, без PUA) строится флагом `--toc`.
- Шаблон `init` лежит в `_parse/ШАБЛОН_изменения.изм.txt` (НЕ в `changes_text/`, чтобы пустое изменение не попадало в сборку).

## Графический редактор изменений (последняя правка пользователя: «нужен GUI»)

- Пользователь снова изменил требование: **нужен GUI** (предыдущая правка «текстовый конечно же» отменена). Решение: desktop-GUI на `tkinter`, без новых внешних зависимостей; это визуальная оболочка над тем же `*.изм.txt`, поэтому текстовый рабочий процесс сохранён. Проверка/сборка идут через `changes_editor.py` + `apply_changes.py`, отчёт — через `json_to_docx.py`.
- `changes_gui.py`: ленивое дерево базы (1.9 МБ, индекс 21216 узлов), поиск, кнопки «Путь в операцию» / «Подставить БЫЛО» / «проверить путь», шапка, список операций (+/−/↑/↓/копия), форма операции, вкладка живого текста `*.изм.txt`, журнал, «строго» / «игнорировать хэш», F5 проверка, F6 сборка, экспорт JSON редакции и DOCX. `_ensure_tkinter()` при отсутствии `tkinter` в текущем Python перезапускает скрипт под интерпретатором с ним; в окружении это `C:\Python313\python.exe` (у Python по умолчанию `tkinter` нет).
