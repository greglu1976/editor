# Структура РЗА (`structure.json`), формат v3

Единая структура **контейнеры (КЭТ) → шкафы → комплекты → ИЭУ** для редактора
электрических схем [`main.py`](main.py). Собирается из каталогов редактора и
наработок по стандартам; спецификация формата — этот файл.

Сейчас в файле **17 КЭТ, 308 шкафов, 339 комплектов (322 с ИЭУ, 17 без ИЭУ),
322 ИЭУ** — всё, что знает каталог редактора (`cabs.all_cabinets()`,
`komplekts.cabinet_komplekts()`, `containers.all_containers()`), включая
пользовательские правки из `cabinets.json`.

## Правила модели

1. **Шкаф состоит из комплектов.** У каждого шкафа есть вложенное поле
   «комплекты» минимум с одной записью. ИЭУ на уровне шкафа **не хранится** —
   только внутри комплекта.
2. **Комплект бывает с ИЭУ или без.** Обязательное булево поле «есть ИЭУ»
   (`true` / `false`) есть у каждого комплекта. Поле «иэу» (вложенные
   устройства) присутствует **только** у комплекта с ИЭУ. Комплект без ИЭУ —
   полноценная запись со своим `id`, номером, назначением и функциями, а не
   пропуск и не ошибка.
3. **Если в описании шкафа одно ИЭУ, оно входит в комплект.** Историческое
   поле `cabinet["ieds"]` с одним устройством переносится в первый комплект
   шкафа (`komplekts.ensure_cabinet_kits()`), после чего удаляется. Сводные
   GOOSE шкафа уходят в это ИЭУ, испытательные блоки — в этот комплект.
   Если владельца определить нельзя (несколько комплектов/ИЭУ), сводные
   таблицы остаются на уровне шкафа с пояснением в «источник …».
4. **Пустых полей не бывает.** Отсутствующие данные просто не пишутся;
   исключение — структурный признак «есть ИЭУ», он пишется всегда.
5. **Связи КЭТ ↔ шкафы — по id.** Шкаф может входить в несколько КЭТ или не
   входить ни в один, поэтому вложение было бы неверным: «контейнеры.шкафы»
   хранит id шкафов, «шкаф.контейнеры» — обратные id КЭТ.

## Как собрать / пересобрать

```bash
python3 tools/recover_kb_docs.py         # 1. исходники таблиц по ИЭУ из БЗ «Исходные»
python3 tools/extract_standards.py       # 2. «Назначение», «Основные компоненты» из PDF
python3 tools/build_structure.py --stats # 3. сборка structure.json (v3)
python3 tools/check_structure.py         # 4. проверка иерархии, ссылок, стыковки
python3 tests/test_structure_docking.py  # 5. тесты: данные, схемы, окна редактора
python3 tests/test_structure_docking.py --no-gui   # без tkinter (только данные)
```

Шаги 1–2 кешируются: `standards/src/*.json`, `standards/text_cache/`,
`standards/extracted.json`. GUI-часть тестов требует Python с `tkinter`;
если его нет, тест сам пропускает окна и проверяет данные.

## Формат

Верхний уровень — объект с разделами `версия`, `описание`, `сущности`,
`источники`, `контейнеры`, `шкафы`. Иерархия вложена, плоских списков
комплектов и ИЭУ больше нет:

```
structure.json
├─ контейнеры[]  (КЭТ)
│  └─ шкафы: [id, ...]              — ссылки
└─ шкафы[]
   ├─ контейнеры: [id, ...]         — обратные ссылки
   └─ комплекты[]                   — вложенные записи, минимум одна
      └─ иэу[]                      — вложенные записи, только при «есть ИЭУ: true»
```

`id` — **ключи каталога редактора**, дополнительный маппинг не нужен:

| Запись | `id` | пример |
|---|---|---|
| контейнер КЭТ | `key` из `containers.py` | `ket-6-1-ii` |
| шкаф | `key` шкафа | `shet-211-01-1` |
| комплект | `komplekts.typical_key(шкаф, индекс)` | `typ:shet-211-01-1:0` |

Номер комплекта «номер» — `1..N` в порядке следования; `id` и номер
согласованы. Усечённый пример (для краткости поля сокращены):

```json
{
  "версия": 3,
  "контейнеры": [
    {"id": "ket-6-1-ii", "код": "КЭТ 6-1-II", "слотов": 8,
     "шкафы": ["shet-211-01-1"]}
  ],
  "шкафы": [
    {
      "id": "shet-211-01-1",
      "шифр": "ШЭТ 211.01-1",
      "полное имя": "Шкаф ...",
      "контейнеры": ["ket-6-1-ii"],
      "комплекты": [
        {"id": "typ:shet-211-01-1:0", "номер": 1, "вид": "Типовой",
         "полное имя": "Комплект 1 шкафа ШЭТ 211.01-1",
         "есть ИЭУ": true,
         "иэу": [{"обозначение": "ИЭУ1", "тип": "МП РЗА",
                  "входные GOOSE": [{"Наименование сигнала": "..."}]}]},
        {"id": "typ:shet-211-01-1:1", "номер": 2, "вид": "Типовой",
         "полное имя": "Комплект 2 шкафа ШЭТ 211.01-1",
         "есть ИЭУ": true, "иэу": [{"обозначение": "ИЭУ2", "тип": "МП РЗА"}]}
      ]
    },
    {
      "id": "ket-arm-op",
      "шифр": "АРМ ОП",
      "комплекты": [
        {"id": "typ:ket-arm-op:0", "номер": 1, "вид": "Типовой",
         "полное имя": "Комплект 1 шкафа АРМ ОП",
         "есть ИЭУ": false,
         "назначение": "Рабочее место оперативного персонала",
         "функции РЗА": ["АРМ ОП"]}
      ]
    }
  ]
}
```

### Поля по уровням

| Уровень | Поля |
|---|---|
| **КЭТ** | `id`, `код`, `название`, `группа`, `типоразмер`, `слотов`, `шкафы`, `описание`, `состав`, `габариты`, `климатическое исполнение`, `степень защиты`, `стандарт`, `архитектура`, `функции`, `примечание`, `источник` |
| **Шкаф** | `id`, `полное имя`, `шифр`, `наименование`, `группа`, `стандарт`, `назначение`, `архитектура ПС`, `класс напряжения`, `защищаемый элемент`, `управляемый элемент`, `вводы питания`, `основные компоненты`, `порты`, `функции ИТС`, `функции МП ИЭУ`, `описание функций ИТС`, `параметры функций ИЭУ`, `применимость`, `дополнительная аппаратура`, `аппаратура связи`, `теги`, схемы (`поясняющая схема подключения`, `эскиз общего вида`, `структурно-функциональная схема`, `схема электрическая принципиальная`), `климатическое исполнение`, `степень защиты оболочки`, `охлаждение`, `контейнеры`, `комплекты`, `источник`; при нескольких владельцах — `входные GOOSE`, `выходные GOOSE`, `испытательные блоки` + `источник …` |
| **Комплект** | `id`, `номер`, `вид`, `полное имя`, **`есть ИЭУ`**, `назначение`, `шифр`, `функции РЗА`, `теги`, `входные аналоговые измерения`, `внутренние дискретные цепи`, `испытательные блоки`, `источник`, `иэу` (только при `true`) |
| **ИЭУ** | `обозначение`, `тип`, `описание`, `входные GOOSE`, `выходные GOOSE`, `источник`; при наличии исходников БЗ — `функциональные клавиши со светодиодной индикацией`, `светодиодная сигнализация`, `команды управления от АСУ ТП`, `аналоговые значения, формируемые ИЭУ`, `отчеты в АСУ ТП` |

Таблицы — массивы строк-объектов с колонками стандарта; списки — массивы
строк. Внешние дискретные сигналы («Дискретные сигналы, формируемые ИЭУ»)
в структуру не переносятся — по требованию образца данных.

### Совместимость

`structure.py` читает файлы версий **2 и 3** (`SUPPORTED_VERSIONS`). В v2
признак «есть ИЭУ» выводится из наличия вложенных «иэу». Проверщик
`tools/check_structure.py` требует строго **v3** — рабочий формат один.

## Стыковка с редактором

Модуль [`structure.py`](structure.py) — единственная точка доступа:

```python
import structure
structure.available(); structure.load(); structure.reload()
structure.container(key); structure.containers_of(cabinet_key)
structure.cabinet(key)              # по ключу каталога или по шифру
structure.cabinets_of(keys)         # шкафы по списку id из КЭТ
structure.kit(key); structure.kit_for(cabinet_key, index); structure.kits_of(cabinet_key)
structure.cabinet_of_kit(kit_key)
structure.ieds_of(kit); structure.has_ied(kit)      # модель «с ИЭУ / без ИЭУ»
structure.cabinets(); structure.containers(); structure.kits(); structure.ieds()
structure.cabinet_label(...); structure.kit_label(...); structure.ied_label(...)
structure.format_cabinet_full(key); structure.format_kit_full(key)
structure.format_container(key); structure.format_record(record); structure.summary()
```

В интерфейсе (`main.py`) все точки входа открывают **один проводник**: дерево
слева (`ttk.Treeview`), карточка записи справа (`tk.Text`), фильтр поиска и
переключатель `Все / С ИЭУ / Без ИЭУ`, строка со счётчиками шкафов,
комплектов и ИЭУ:

* **Шкафы → Каталог…** → «Структура» — шкаф и все его комплекты;
* **Комплекты → Каталог…** → «Структура» — комплект в контексте шкафа;
* **Шкафы → Структура…** — весь файл: КЭТ, шкафы, комплекты, ИЭУ;
* **Ctrl+E** — структура выделенного на схеме шкафа или контейнера КЭТ
  (ключи берутся из `self.elements` по id из `selected_elements`);
* каталоги шкафов и комплектов, а также диалог выбора комплекта показывают
  счётчики «с ИЭУ / без ИЭУ» и фильтр «Состав»;
* кнопки окна: «Копировать», «Перечитать structure.json» (**F5**), «Сводка»,
  «Закрыть» (**Esc**). Комплекты без ИЭУ — отдельный тип узла с подписью
  «без ИЭУ»; ИЭУ всегда вложено в комплект.

### Что делает «Перечитать structure.json» (F5)

Единственный источник данных окна — готовый файл `structure.json` в папке
проекта (`structure.DEFAULT_PATH`, сейчас `G:\editor\structure.json`, ~2 МБ).
Путь и время изменения файла показаны в шапке окна и в корневом узле дерева.
`structure.py` кэширует документ и индексы при первом чтении, поэтому без
перечитывания окно продолжало бы показывать старый снимок, даже если файл на
диске уже заменён.

Кнопка вызывает `structure.reload()` → `structure.load(force=True)`: кэш
сбрасывается, JSON читается с диска заново, индексы строятся заново, дерево,
карточка и счётчики перерисовываются. **Кнопка не запускает
`tools/build_structure.py`, не читает `cabs.py` / `cabinets.json` /
`komplekts.json`, не обращается к PDF и базе знаний и ничего не пишет на диск.**
Если файл в этот момент отсутствует или испорчен, показывается ошибка.

Практическое следствие: поправив шкаф или комплект в каталоге редактора,
сначала нужно пересобрать файл (`python3 tools/build_structure.py`), и только
потом нажать F5 в открытом окне. Сама по себе кнопка новых данных не создаёт.

Ключ элемента схемы (`element.cabinet_key` / `element["cabinet"]["key"]`),
ключ комплекта (`komplekts.typical_key(cabinet_key, index)`) и ключ КЭТ
(`element.container_key`) — это и есть `id` записей структуры; проверено на
реальных схемах из `schemes/` (17/17 шкафов, 27/27 комплектов).

## Известные пробелы

1. **`standards/src` пока пуст.** `tools/recover_kb_docs.py` в текущем
   окружении не восстанавливает исходники БЗ, поэтому «толстые» таблицы по
   ИЭУ (ФК, светодиодная сигнализация, команды АСУ ТП, аналоговые значения,
   отчёты) в структуру не попадают. GOOSE и описания приходят из
   `cabs_signals.json` и каталога.
2. **Внешние дискретные сигналы** справочно есть в `cabs_signals.json`, но в
   структуру не переносятся (требование образца).
3. **Толстые колонки таблиц СТО** (состояния индикации «0»/«1», режим
   сигнализации, обозначение на лицевой панели) в наработках потеряны —
   исходники БЗ хранят только наименования. Полные колонки есть в PDF;
   выгрузка — отдельная задача.
4. **«Основные компоненты шкафа»**: наименования и характеристики склеены в
   одну строку — в PDF это соседние ячейки, переносы строк внутри ячейки не
   позволяют разрезать их надёжно. Количество вынесено отдельно.
5. **21 шифр из PDF** не имеет пары в каталоге редактора (например,
   `ШЭТ441.11-1`, `ШПДС1-Х-Х`, `ОЭТ071.01-0`). Чтобы они попали в структуру,
   их нужно добавить в `cabs_sto.py`. Часть СТО (ШСО/ШСК, алгоритмы ОБР)
   вообще не содержит разделов «Шкаф … типа ШЭТ …».
6. **Сводные данные без единственного владельца**: у 6 шкафов с несколькими
   комплектами/ИЭУ сводный GOOSE и испытательные блоки остаются на уровне
   шкафа — с полями «источник GOOSE» / «источник испытательных блоков».
7. У **нетиповых и пользовательских** шкафов (копии, самодельные) поля
   стандартов пустуют по определению — структура отражает то, что есть в
   каталоге. Два шкафа с одним ИЭУ (`shavr-04`, `shpa-110`) удалены
   пользовательскими правками `cabinets.json` и в структуру не входят.
